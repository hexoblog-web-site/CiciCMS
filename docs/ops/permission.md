# 权限模型（重点）

这一页是整个程序最核心的设计。看懂它，你就知道为什么升级不会丢数据、为什么上传目录不怕被传马。

## 为什么分区

划分依据有两条，缺一不可：

1. **升级时谁该被覆盖** —— 代码该换，数据不该动
2. **运行期谁能写、谁能执行** —— 能写的地方不能能执行，能执行的地方不能能写

第二条是安全上的老规矩：**如果同一个目录既能被写入又能被执行，那它就等于一个远程代码执行的入口。**

## 三个区

| 分区 | 目录 | 运行期可写 | 运行期可执行 | 部署权限 | 升级时 |
| --- | --- | --- | --- | --- | --- |
| **系统区** | `includes/` `admin/` `install/` | 否 | 是（PHP） | 只读 555 | 整体覆盖 |
| **内容区** | `content/` | 是 | 否（两处例外） | 必须可写 755 | **保留，绝不覆盖** |
| **入口** | 根目录的 `.php`、`config.php` | 仅 `config.php` 装一次 | 是 | `config.php` 装完 644 | 覆盖 php，保留 `config.php` |

一句话记法：

> **代码区只执行不写入，数据区只写入不执行。**

所以升级永远只有一句话：**覆盖 `includes/`、`admin/`、`install/`，`content/` 和 `config.php` 不要动。**

## 为什么这样分就安全

想象一下最坏情况：**有人找到办法，通过某个上传功能往你的服务器写了一个 `shell.php`。**

| 他能写进哪 | 后果 |
| --- | --- |
| 系统区（`includes/`） | 目录只读，写不进去 |
| 内容区（`content/uploads/`） | 能写进去，但那个目录的脚本**不会被执行**，文件躺在那儿是死的 |
| 站点根目录 | 能写，但生成器只允许写 `.html/.xml/.txt/.json` |

也就是说，**"能写"和"能执行"被拆到了两个地方**，攻击者拿到其中一个，都没法直接变成命令执行。

## 两处例外（必须知道） {#exceptions}

上面那句"内容区只写不执行"有**两个例外**。它们存在的原因不同，风险也不同。

### 例外一：`content/plugins/` —— 能写 **也** 能执行 {#plugins}

插件本身就是 PHP：`content/plugins/<id>/plugin.php` 会被 `include` 执行。

所以这个目录：

| 属性 | 值 |
| --- | --- |
| 必须可写？ | 是（否则装不了插件） |
| 会被执行？ | 是（否则插件没法工作） |
| 风险等级 | **最高** |

::: danger 用一句大白话说清楚
**能往 `content/plugins/` 放一个 `plugin.php`、并且点一下"启用"的人，等于能在你的服务器上执行任意 PHP。**

要同时做到这两件事，前提是**已经登录后台**并且**有写文件的权限**。所以门槛不低，但它是全站唯一一处"写进去就等于能执行"的地方。
:::

**怎么办**

| 做法 | 效果 |
| --- | --- |
| **不需要插件就删掉整个 `content/plugins/`** | 这一类风险直接归零 ← 最推荐 |
| 只装自己写的、或者官方仓库的插件 | 去掉最大的来源 |
| 装之前读一遍 `plugin.php`，看有没有 `eval`、`base64_decode`、奇怪的外连地址 | 挡掉大部分后门 |
| 不用的插件停用 | 停用即不加载，减少暴露面 |

### 例外二：`content/data/cache/tpl/` —— 编译后的模板缓存 {#cache}

标签模板（`{cici:xxx}`）在第一次渲染时会被**编译成 PHP 代码**缓存起来，之后 `include` 这个缓存文件。

| 属性 | 值 |
| --- | --- |
| 会被执行？ | 是（`include` 缓存文件） |
| 内容从哪来 | 由你写的模板编译而来 |
| 风险等级 | 中 |

**为什么风险比插件低**：缓存内容不是随便什么文件，而是"你写的模板"编译出来的。要利用它，攻击者得先能改模板（那已经等于拿到了后台管理员权限）。

**怎么办**：不用特别做什么。它必须可写，否则模板改不动。`content/data/` 整个目录被 `.htaccess` / Nginx 规则拒绝外部访问，这一点已经挡住了直接请求。

## 权限怎么设

### Linux / 宝塔 / 虚拟主机

```bash
cd /www/wwwroot/example.com

# 内容区：可写
chmod -R 755 content

# 程序代码：只读
chmod -R 555 includes admin install

# 配置文件：只读
chmod 644 config.php

# 属主改成 PHP 运行用户（宝塔通常是 www）
chown -R www:www .
```

::: danger 三个常见错误
**① 用 777**

有些教程让你 `chmod -R 777`。别这么做：

- 等于任何进程都能改你的程序文件
- 部分主机开了 `safe_mode` 遗留限制，777 的 PHP 反而拒绝执行，报 500
- 共享主机上，同服务器其他用户可能读写你的文件

**755 就够了**，关键是**属主对**。

**② 代码区用 111 或 `--x`**

有人以为"只给执行不给读"更安全。错：

- 目录需要 **r** 才能列出文件名，需要 **x** 才能进入
- 只给 x，PHP 无法 `include` 文件，整站 500
- 正确是 **555**（r-xr-xr-x）

**③ `includes/` 属主是 root**

如果程序文件属主是 `root`、PHP 运行用户是 `www`，那在线更新时 `chmod` 会失败。程序会**直接拦下并提示**，不会写到一半——但你就得手动改权限了。

正确做法：`chown -R www:www includes admin`，然后用 555 限制写权限（属主是 www 但位是 555，也能被程序临时 chmod 开）。
:::

### Windows / IIS

给 `IIS_IUSRS`（或应用程序池身份）这两类权限：

| 目录 | 权限 |
| --- | --- |
| 根目录、`content/` | 修改 / 写入 |
| `includes/`、`admin/` | 读取 + 执行 |

Windows 上不要指望 `chmod`，权限靠 ACL。

## 后台自检

「系统设置 → 目录权限自检」会按上面的表逐项核对：

| 颜色 | 含义 |
| --- | --- |
| 绿 | 符合预期 |
| 黄 | 还没落实，建议处理 |

::: warning 它查不到什么
- **`content/plugins/` 本来就必须可写**，自检不会提示它，但它是风险最高的目录
- 自检查的是**权限位**，不是"有没有被入侵"
- 它不会告诉你 `config.php` 能不能被外部下载 —— 那要靠 Web 服务器配置，见 [部署配置](/ops/deploy#部署检查清单)
:::

## 常见错误对照

| 你做的 | 结果 | 怎么修 |
| --- | --- | --- |
| `chmod -R 777 .` | 可能 500，且等于敞开大门 | 改回 755 / 555，属主改对 |
| `chmod -R 555 .` | 生成静态时"写入失败" | `content/` 和根目录改回 755 |
| 只把 `content/` 设 755，根目录还是 555 | 首页生成不出来 | 根目录也要 755 |
| `includes/` 属主 root | 在线更新被拦下 | `chown -R www:www includes` |
| 删了 `content/plugins/.htaccess` | Apache 下插件 PHP 可被直接访问 | 从原包里拷回来 |
| Nginx 没配 ③ 那条规则 | 插件 PHP 可被直接执行 | 补规则，见部署页 |

## 根目录可写这件事

必须承认：**站点根目录是"可写 + 可执行"的**。

因为静态页要写进根目录，而 `index.php` 又必须可执行。这是纯静态方案的固有矛盾，不是配置失误。

程序做的缓解：生成器只允许写 `.html/.xml/.txt/.json`（`build_allowed_ext()`）。

彻底的解法是"输出目录与代码目录分离"——静态页生成到 `public/`，PHP 入口放在它外面。这需要改 URL 结构与部署方式，是 2.x 的方向。当前版本没有这么做。
